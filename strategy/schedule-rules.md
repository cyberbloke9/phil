# schedule.json pacing rules

Moved verbatim out of the `_comment` field of `strategy/schedule.json` on
2026-09-29. `loop.sh` and `core/validate.py` read only `next_full_cycle_after`
and `min_full_cycles_per_day`; the prose below is the agent's own rulebook
for when to set them. Amend it here, not inline in the JSON.

AGENT-EDITABLE self-pacing. The cloud routine ticks hourly and I cannot change that, but I decide which ticks deserve a FULL cycle (scan + research + bet) and which are LIGHT (settle + monitor open positions, then stop). Set next_full_cycle_after when a full cycle would be wasted — e.g. no candidate resolves for hours, or research sources are unavailable. A tick always settles and monitors regardless; skipping those is not allowed. LIGHT ticks skip only scan+research: if resolve.py settles ANYTHING on a light tick, that same tick writes the retro and applies any pre-registered grading — settlement grading is never deferred to a later tick (DEEP-2026-08-05: b21e42c123a1 settled on the 06:24Z light tick, its retro was 'deferred to next full cycle', and the 08:15Z full cycle then saw '0 settled this cycle' and wrote nothing — the $5 loss went ungraded for 23h). DEEP-2026-08-23 addition: if a settled row is outside-view-veto or wide-spread-veto, the SAME commit as its settlement retro must extend the playbook counterfactual ledger table (new row + re-summed totals + side split) -- RETRO-20260822-1314 graded the TI VISION/Yandex veto narratively and left the table stale; a veto retro without a table edit is a violation on its face. DEEP-2026-09-02 clarification: 'settles ANYTHING' means ledger bets AND forecasts alike -- the 2026-09-01 08:19Z LIGHT tick settled 2 forecasts (Iran daa8218bb25d watch item, JPM 38e50222e784) and deferred grading 'to the next FULL retro' on a claimed ledger-only reading of this rule; no later cycle picked them up and the deep retro had to grade them 19h late. A LIGHT tick that settles only forecasts still writes the retro (RETRO-20260901-2222 and RETRO-20260902-0212 both did this correctly). RETRO-20260908-2250 clarification: this applies to TRIGGERED ticks too -- a TRIGGERED cycle is scoped in its CANDIDATE set, never in its settlement duties; the 2026-09-08 18:59Z triggered cycle saw forecast 8c604893bdea settle and wrote 'no retro, scoped to the trigger candidate', and the grading landed four hours late on the next FULL cycle. DEEP-2026-09-15 hygiene: the reason field holds the CURRENT SET block plus at most one line noting the previous clearance; do not append PRIOR history -- git and cycles.log already keep it.
